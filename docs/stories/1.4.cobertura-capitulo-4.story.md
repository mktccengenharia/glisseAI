## Descobertas técnicas (por que não foi um simples "replicar o parser do Cap. 3")

1. **Extração `-layout` desalinha dados**: `pdftotext -layout` produz duas sub-tabelas (descrição e porte/valores) com ritmos de linha independentes que desalinham verticalmente assim que uma descrição quebra em 2 linhas — o valor "colado" numa linha podia pertencer à linha anterior ou seguinte, silenciosamente. Resolvido usando `pdftotext -table` (modo otimizado para tabelas do próprio pdftotext), que corrige isso na extração.
2. **6 esquemas de coluna diferentes** (não 1 fixo como no Cap. 3), catalogados exaustivamente contra o texto-fonte:
   - `porte_oper` — Porte + Custo Operacional (exames simples: ECG, audiometria etc.)
   - `porte_oper_aux` — + Nº de Auxiliares (ex: Endoscopia)
   - `porte_oper_anest` — + Porte Anestésico
   - `porte_oper_aux_anest` — + Auxiliares + Anestésico (igual ao Cap. 3)
   - `porte_oper_doc_incid` — + Custo Filme/Documentação + Nº de Incidências (Radiologia)
   - `porte_oper_doc_ur` — + Custo Filme/Documentação + UR (Medicina Nuclear)
3. **"UR" = Unidade de Radiofármaco** (não "Unidade de Radiologia", hipótese inicial errada, corrigida ao achar a definição oficial no próprio texto-fonte, seção "INSTRUÇÕES ESPECÍFICAS PARA MEDICINA NUCLEAR"). Quase sempre aparece como `*` — confirmado que isso remete a uma tabela de preços **externa** do Colégio Brasileiro de Radiologia, não a um valor numérico presente no documento. Gravado como texto bruto (nunca um número inventado).
4. **"Incid." confirmado por autoconsistência dos dados**: nomes de procedimento como "RX – Crânio – 3 incidências" batem exatamente com o valor da coluna (3).
5. **Ordem/abreviação dos cabeçalhos varia por edição** (ex: 2014 mostra "UR ou DOC. Porte Oper." em vez de "Porte Oper. ou Doc. UR"): detecção de schema trocada de comparação de string exata para reconhecimento por palavra-chave, robusto a ordem e abreviação.
6. **Vazamento de menções a código dentro de blocos de OBSERVAÇÕES**: texto explicativo às vezes cita um código real no meio da prosa (ex: "4.09.01.17-3 Abdome inferior masculino..., não são remunerados concomitantemente"). Corrigido: dentro de um bloco de observação, só aceita uma linha como registro novo se já tiver porte+valores colados na mesma linha (dado tabular real), nunca via lookahead — prosa nunca é dado tabular.

7. **AC7:** Embeddings devem ser gerados para os novos registros (busca semântica cobrindo o Capítulo 4 também).
8. **AC8:** `npm run lint`, `npm test`, `npm run build` continuam passando.

## Dev Notes

**Decisão consciente de não cobrir 100% das notações**: durante a investigação apareceu uma terceira notação de porte ("0,10 de 1A" — porte fracionário para componentes de painel laboratorial, ex: sorologias múltiplas do mesmo tubo). Modelar isso corretamente exigiria mais um schema (fração + porte de referência) e mais uma rodada de migration. Dado que o projeto já tem precedente estabelecido de importar códigos sem porte determinável como stubs pesquisáveis (Capítulo 3, commit anterior: "recupera 43 dos 51 códigos sem porte determinável como stubs pesquisáveis"), optou-se por manter esse padrão em vez de perseguir cada notação exótica indefinidamente. Esses códigos continuam buscáveis por nome/código, só não exibem porte/valor.

**Processos órfãos**: durante a validação, ~25 processos `next dev` de sessões de teste anteriores ficaram rodando em background (o `pkill -f "next dev"` do git-bash não os alcança de forma confiável no Windows), causando um conflito de arquivo (`EINVAL` no `.next`) ao subir mais um servidor de teste. Higienizado via `Stop-Process` direcionado por `CommandLine` (PowerShell), preservando o processo de geração de embeddings em andamento e ferramentas não relacionadas (Adobe, chrome-devtools-mcp).
