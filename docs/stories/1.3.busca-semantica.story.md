## Acceptance Criteria

1. **AC1 — Embeddings locais:** `/api/search` deve gerar embeddings via modelo open source rodando dentro da própria função serverless (`@huggingface/transformers`, modelo `Xenova/multilingual-e5-small`), sem chamada a API externa de embeddings.
2. **AC2 — Fallback semântico:** quando busca por código, full-text e ILIKE não encontram nada, a rota deve tentar busca por similaridade de embeddings antes de desistir.
3. **AC3 — Migration documentada:** `supabase/schema.sql` deve conter a extensão `vector`, a coluna `embedding` e a função RPC de similaridade, com instrução clara de aplicação manual (mesma convenção das seções anteriores).
4. **AC4 — Script de backfill:** deve existir um script standalone para gerar embeddings de todos os procedimentos já importados, idempotente (resume de onde parou).
5. **AC5 — Degradação graciosa:** enquanto a migration não for aplicada, a busca deve continuar funcionando normalmente (sem crash), apenas sem o fallback semântico, com log claro do motivo.
6. **AC6 — Reversão do controle de acesso:** `src/middleware.js`, `/login` e `/api/auth/login` devem ser removidos; app volta a ficar aberto.
7. **AC7 — Sem regressão:** `npm run lint`, `npm test` e `npm run build` continuam passando.

## Dev Notes

Modelo escolhido (`Xenova/multilingual-e5-small`, 384 dimensões, quantizado `q8`, ~120MB): bom equilíbrio entre qualidade multilíngue (cobre português) e tamanho para rodar em função serverless. Convenção do modelo e5 exige prefixar `"query: "` em textos de busca e `"passage: "` em textos indexados — implementado em `src/lib/embeddings.js`.

Carregamento é preguiçoso (lazy singleton) para não travar o cold start de rotas que não usam busca semântica. Fluid Compute (Vercel) reaproveita instâncias entre requisições, então o custo de carregar o modelo (~50s na primeira chamada, medido localmente) só acontece uma vez por instância, não por requisição.

## Validation Results

- `npm run lint`: ✅ sem warnings/erros
- `npm test`: ✅ 20/20 (sem novos testes automatizados para o modelo em si — ver justificativa abaixo)
- `npm run build`: ✅ passa, `next.config.js` com `serverComponentsExternalPackages` evita que o bundler processe os binários nativos do `onnxruntime-node`
- Teste manual direto do módulo (`embedQuery`/`embedPassage`, fora do Next): embeddings de 384 dimensões gerados corretamente; similaridade de cosseno para `"tirar próstata"` vs `"RTU de Próstata"` = 0.8957, contra 0.8242 para um distrator irrelevante (`"Holter de 24 horas"`) — confirma que o ranking semântico funciona antes mesmo de aplicar a migration
- Smoke test em `/api/search` contra Supabase real (migration ainda não aplicada): retorna `200` com `results: []` e loga `"Busca semântica indisponível (migration aplicada?): Could not find the function public.match_cbhpm_procedures..."` — confirma degradação graciosa (AC5)

**Por que não há teste automatizado do modelo em si:** baixar ~120MB de pesos a cada execução do CI tornaria o pipeline lento e frágil (depende de rede externa no runner). A lógica determinística (fallback em cascata, tratamento de erro) já está coberta indiretamente pelos testes existentes de `/api/search`; a qualidade do ranking semântico foi validada manualmente (acima) e deve ser reconfirmada pelo usuário após aplicar a migration e rodar o backfill com dados reais.
